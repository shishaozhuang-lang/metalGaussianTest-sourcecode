# dazhongkafei 性能瓶颈分析：带宽 vs 算力

> 附属于 [REPORT.md](REPORT.md)（双平台性能测试）与 [Vsync-vs-Offscreen-Analysis.md](Vsync-vs-Offscreen-Analysis.md)（模式差异）。
> 本文回答：Mac 和 iPhone 上 3DGS 渲染的瓶颈到底是**内存带宽**还是**算力**，给出定量证据链。
> 测试日期 2026-11-11，冷态离屏 benchmark（每轮间 60s+ 冷却，避免热节流污染数据——热态曾使 iPhone 帧耗时虚高 52%：28.97ms vs 冷态 19.11ms）。

## 结论（先答）

**两平台的第一瓶颈都不是带宽，也不是峰值算力，而是顶点着色器阶段的吞吐-延迟混合受限（vertex-issue/latency bound）：**

| 平台 | 帧耗时分解（540×960 离屏冷态） | 主瓶颈 |
|---|---|---|
| Mac (M5) | **顶点 11.7ms（93%）** + 片元 0.9ms（7%） | 顶点阶段，延迟受限（带宽利用率仅 8%） |
| iPhone 17 Pro Max | **顶点 16.5ms（87%）** + 片元 2.6ms（13%） | 顶点阶段，延迟受限（带宽利用率 ~20%） |

- **算力（ALU）**：顶点理论需求 Mac 0.23 / iPhone 0.12-0.16 TFLOPS，仅硬件峰值的 5-7% —— 远未饱和
- **带宽（DRAM）**：顶点数据流 Mac 16.4GB/s（8% 峰值）/ iPhone 11.7GB/s（~20% 峰值）—— 远未饱和
- **实际约束**：顶点阶段 192MB/帧的**随机访问延迟** + 顶点发射吞吐。GPU 核心数少/占用率低时，内存延迟无法被足够的并行顶点掩盖
- **片元阶段**：只在 ≥1080p 才开始显著（iPhone 1080 占 34%，2160 占 60%+）；540 下两平台片元都 <15%，是 TBDR（tile memory blend）带来的结构性优势
- **平台差距**：iPhone 顶点慢 1.41×（≈ 核数比 6:10），片元慢 2.23×（填充率/带宽差距大于核数比）

## 证据链（五组实验）

### 实验 1：SH 阶数扫描 —— 顶点数据量 −70%，帧耗时几乎不变

SH3（130B/splat 顶点读）→ SH1（70B）→ SH0（40B）：

| 配置 | Mac 540 | iPhone 540 |
|---|---:|---:|
| SH3（默认） | 12.67ms | 19.11ms |
| SH1 | 12.76ms | 18.24ms |
| SH0 | 12.85ms | 17.77ms |
| 差异 | **<2%（噪声级）** | **7%** |

若顶点带宽饱和，数据量减 70% 应显著提速；实测 Mac 无变化、iPhone 仅 7%。
**→ 顶点 DRAM 带宽不是第一瓶颈**（与理论 8-20% 利用率吻合）。
（同时说明 `.sphericalHarmonicsTexture` 等 SH 带宽优化对该场景收益有限。）

### 实验 2：分辨率扫描 —— 片元占比低，顶点主导

像素数 1/16 → 16×（离屏冷态）：

| 分辨率 | Mac | iPhone |
|---|---:|---:|
| 270×480 (0.13Mpx) | 13.40ms | **16.57ms** |
| 540×960 (0.52Mpx) | 12.65ms | **19.11ms** |
| 1080×1920 (2.07Mpx) | 14.69ms | **25.00ms** |
| 1440×2560 (3.69Mpx) | — | **31.54ms** |
| 2160×3840 (8.29Mpx) | **26.65ms** | **49.90ms** |

线性拟合 `t = V + k·像素`：

- **Mac：V = 11.34ms + 1.84ms/Mpx**（540 片元占 8%；2160 占 57%）
- **iPhone：V = 16.58ms + 4.03ms/Mpx**（5 点拟合，拟合误差 <0.5ms；540 片元占 11%；1080 占 33%；1440 占 47%；2160 占 67%）

像素缩到 1/16，iPhone 帧耗时仅降 13% → **87% 的时间花在与像素数无关的顶点处理**。
**→ 当前测试分辨率（540/1080）下片元填充率不是主导；2160 级别才翻转。**

### 实验 3：模型规模扫描 —— 顶点时间随 splat 数超线性

hailuo（42.9 万可见）vs dazhongkafei（148.3 万可见），同视角同分辨率（Mac）：

| 模型 | splat 比 | 顶点+固定时间 | 帧耗时 |
|---|---:|---:|---:|
| hailuo 540 | 1× | 2.77ms | 3.24ms |
| hailuo 2160 | 1× | 2.77ms | 10.33ms |
| dzk 540 | 3.45× | 11.72ms | 12.65ms |
| dzk 2160 | 3.45× | 11.72ms | 26.65ms |

- 顶点时间比 = 11.72/2.77 = **4.23× > splat 数比 3.45×（超线性 23%）**
- 解释：hailuo splat 数据 13.8MB + SH 39MB ≈ 53MB 可基本驻留 GPU 二级缓存；dzk 47MB + 133MB = 180MB 远超缓存 → 顶点随机访问落到 DRAM，延迟与带宽约束显现
- 顶点访问模式本身是**深度序索引 → Morton 序数据**的间接随机跳转（排序索引顺序读，但其指向的 splat/SH 数据在内存中按 Morton 局部性排列，深度序遍历=空间跳跃），局部性差

**→ 顶点阶段是 splat 数量的超线性函数，规模越大越接近带宽/延迟墙。**

### 实验 4：GPU 通道拆分（Metal System Trace，按 command buffer 归因）

| 模式/平台 | Vertex | Fragment | 合计 |
|---|---:|---:|---:|
| Mac vsync（独占+高频） | 3.3ms | 10.2ms | 13.4ms |
| Mac 离屏（3 并发+降频） | **9.8ms** | 12.5ms | 22.3ms |
| iPhone 540 vsync | p50 15.8ms | p50 8.2ms | 21ms 帧间隔 |
| iPhone 1080 vsync（热态） | p50 33.7ms | p50 10.9ms | 42ms 帧间隔 |

- 3 并发对顶点伤害 3×（3.3→9.8ms）：顶点吞吐饱和的证据——多个 command buffer 的顶点阶段互相争用发射资源
- iPhone 540 顶点 p50 15.8ms 与离屏分解的 16.5ms 一致 ✓
- trace 的 Fragment 数字含 tile 结算/合成串行成分，偏大；以分辨率差分法（实验 2）为准
- （iPhone 1080 的 33.7ms 为昨天热态录制，参考价值低——热节流使顶点慢 2.1×）

### 实验 5：理论需求 vs 硬件峰值

| 指标 | Mac (M5, 10 核) | iPhone (A19 Pro, 6 核) | 饱和度 |
|---|---:|---:|---|
| 顶点 ALU 需求（~2kFLOP/splat × 148 万 / 帧时） | 0.23 TFLOPS | 0.12-0.16 TFLOPS | 峰值的 5-7% |
| 顶点 DRAM 流量（130B/splat × 148 万 / 帧时） | 16.4 GB/s | 11.7 GB/s | 峰值的 8% / 20% |
| 顶点调用率（148 万 × 4 顶点 / 顶点时间） | 605M/s | 474M/s | 名义 1-2G/s 的 30-50% |
| CPU encode | 0.08ms | 0.086ms | — |

**没有任何一项资源达到饱和。** 瓶颈形态是：顶点 shader 每 splat 2 次随机内存访问（splat 32B + SH 90B），核心数/占用率不足以完全掩盖延迟 → GPU 在"等内存"与"发射顶点"之间空转。这类负载的优化解法不是加带宽而是加并行度（更多核心/更多 in-flight 顶点）或改访问模式。

## 瓶颈的准确定位（按 540 推荐配置）

```
iPhone 17 Pro Max @ 540×960, 19.1ms/帧:
├─ CPU encode            0.09ms   (0.5%)   ← 无关
├─ GPU 顶点阶段         16.5ms   (86%)   ← ★ 第一瓶颈: 顶点吞吐+延迟
│    ├─ ALU 利用          ~7% of peak
│    ├─ DRAM 带宽利用     ~20% of peak
│    └─ 受限原因: 随机访问延迟无法被并行顶点完全掩盖
└─ GPU 片元阶段          2.6ms   (14%)   ← 次要: 1080 时升到 34%

Mac (M5) @ 540×960, 12.65ms/帧:
├─ CPU encode            0.08ms   (0.6%)  ← 无关
├─ GPU 顶点阶段         11.7ms   (93%)   ← ★ 同样顶点主导
└─ GPU 片元阶段          0.9ms   (7%)
```

## 平台差异的定量解释

| 阶段 | iPhone/Mac 性能比 | 对应硬件差异 |
|---|---:|---|
| 顶点吞吐 | 1.41× 慢 | GPU 核 6:10 = 1.67× —— 顶点吞吐大致跟核数走，略好于核数比（单核顶点发射能力相近） |
| 片元填充 | 2.19× 慢 | 大于核数比 —— A19 Pro 的 tile/ROP 吞吐与 DRAM 带宽（~60 vs ~200GB/s）差 3.3×，片元对带宽更敏感；2160 下片元 iPhone 33.4ms vs Mac 15.3ms |
| CPU 排序 | 100 vs 68.5ms（1.46× 慢） | 单核性能差 |
| 热设计 | 热态帧耗时 +52% | 手机无风扇，持续满载 10 秒级即节流；Mac 无此问题 |

**iPhone 掉帧的根因排序**：① 顶点阶段吞吐不足（86% 帧时）→ ② 热节流（长时间运行再吃掉 52%）→ ③ 高分辨率时片元填充率（1080 占 34%）。

## 对优化路径的启示（修正之前的建议）

1. **SH 纹理化/SH 降阶收益有限**（实验 1：≤7%）——此前建议高估了带宽收益。
2. **有效方向——降低顶点阶段工作量**：
   - CPU culling 更激进（当前视角已剔 26%；提高 opacity 阈值、贡献度剔除可再剔）
   - 视锥外 splat 不发射顶点（frustum culling 在 CPU 排序时已做，GPU 端 VS 早退仍占发射槽位）
   - **按 tile 分块渲染**（把 148 万 splat 分给 32×32 tile 各自的可见集，顶点只需处理落在本 tile 的 splat）——这是结构性解法，可把顶点量降 5-10×
3. **提高顶点并行度**：增加 in-flight draw 或拆分多个小 draw（当前单 draw 1448 instances 一次发射）。
4. **不要指望降分辨率救 540**（像素已只占 13%）；但 1080→540 仍值（片元从 34%→11%）。
5. **iPhone 散热是第二大敌人**：任何优化同时降低功耗（顶点数减少 = 带宽+ALU 同降）会双重收益。
